Palier 2 (the other 10 forms -- `ProfileModal`, `AdminPanel`, `ChannelSettingsModal`, `CreateChannelModal`, `SearchModal`, `ChatView`, `VoiceView`) is a separate, not-yet-started follow-up plan, per `docs/superpowers/specs/2026-08-11-forms-ui-cleanup-design.md`. One real design dispute worked through during implementation, worth knowing about before touching `RangeSlider.tsx` again: reading the committed value straight off `event.target` at commit time does NOT work in this project's actual React/jsdom/Testing-Library setup -- React resets a controlled `<input>`'s DOM value on the change event when nothing updates the controlling prop, so the value must be captured in a `useRef` the moment `onChange` fires, kept in sync against *external* prop changes via a `useEffect([value])` (or a parent-driven update, e.g. an async fetch resolving post-mount, goes stale), and `onKeyUp` must filter to value-changing keys only (arrows/Home/End/PageUp/PageDown) or merely tabbing past the slider fires a spurious commit. The final whole-branch review also caught and got fixed a CSS cascade bug of the same shape as the drift this lot exists to remove: `.form-input`'s `outline: none` lived in its base (non-focus) rule, so a pre-existing global `input:focus-visible { outline: 2px solid #00a8fc }` rule still won on focus, stacking the old cyan ring on the new violet halo -- fixed by moving `outline: none` into the `:focus-visible` variant, and by adding the equivalent for `.form-range`, which had no focus treatment at all.

Extends two primitives along the way: `TextField` gains an optional `prefix` slot (the `#`/`◖))` icon in front of a channel name, rendered via a NEW `.form-input-group` class specifically so it doesn't collide with the pre-existing `.channel-name-field` class that `CreateChannelModal` -- not part of this lot -- still depends on); `RangeSlider` gains an optional `trailing` slot (the per-sound "Preview" button next to each volume slider), with its Palier-1 dual-commit ref/effect/key-filter mechanism left completely untouched and re-verified line-by-line given that mechanism's dispute history. `ChannelSettingsModal` also gains a real `<form>` for the first time (Enter in the name field now saves, confirmed live via Playwright), and its name field's accessible name simplifies from a redundant `aria-label="Name of {channel}"` override to the plain, static "Channel name" matching its visible label.

  **The real lesson from this lot**: several of the app's existing CSS rules use descendant selectors (e.g. `.profile-fields input`) that are MORE specific than the new primitives' own base class (`.form-input`) -- so migrating a form's markup to the new primitives is not enough by itself; every old rule that would still match the primitive's internal elements has to be found and deleted/trimmed too, or the OLD styling silently keeps winning and the migration achieves nothing visually. Several of these old rules are shared, multi-selector blocks that also serve OTHER, not-yet-migrated forms (`VoiceView`, `AdminPanel`, `CreateChannelModal`) -- only the specific selectors belonging to the form actually being migrated can be removed from those shared rules; the rest must survive untouched. This was verified via grep before every deletion in both tasks, and the highest-risk case (`.channel-name-field`/`.create-channel-form select`, still live for the out-of-scope `CreateChannelModal`) was independently re-confirmed byte-for-byte untouched by a fresh reviewer reading the current files directly, not just the diff. **Any future Palier 2 work must budget real time for this same CSS archaeology per form** -- it is not a one-time cost paid off by Palier 1, since each additional form surfaces its own set of shared/dead rules.

  Live-verified via Playwright against an isolated throwaway database (never the shared dev DB): Profile modal's Username/Email/About-me fields and all 5 sound sliders render with the unified style and a single clean focus ring (no double outline, confirming the Palier 1 final-review CSS fix holds in a real browser); Channel settings modal's name field shows its `#` prefix correctly inside the new bordered group, and pressing Enter in the name field now saves and closes the modal (previously did nothing).

## Security fixes

- SVG attachments were served with `Content-Disposition: inline` (any client-supplied `image/*` MIME type was trusted), and the web client linked directly to that URL for anything it treated as an image -- a stored XSS, since SVG can carry `<script>`/event handlers that execute when opened as a top-level document. Fixed by restricting inline rendering to an explicit raster-image allowlist (`server/src/routes/messages.ts`'s `INLINE_SAFE_MIME_TYPES`, mirrored client-side in `web/src/layout/ChatView.tsx`); anything outside it, including SVG, is always forced to download, plus `X-Content-Type-Options: nosniff` and a restrictive CSP on that response. **Do not widen that allowlist back to a bare `startsWith("image/")` check.**

**Why chat messages use a cap instead of true virtualization** (don't re-attempt windowed rendering without reading this first): this test environment (jsdom) implements neither `Element.scrollTo`, `ResizeObserver`, nor a real layout engine (`getBoundingClientRect` always returns zeros). A virtualization library (evaluated: `react-window` v2, a very different and simpler API than v1) depends on all three to measure its container and rows. That means a windowed rewrite of `ChatView.tsx`'s message list could not be verified by any automated test here -- it would ship as a large rewrite of an always-on feature with no working safety net beyond "it typechecks." Asked the user directly; they chose the safer bound (see `chat-message-cap` above) over shipping that risk. If real virtualization is wanted later, it needs to happen where actual browser testing is possible (Playwright against a real browser engine, or manual verification), not here.
