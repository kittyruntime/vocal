  **The real lesson from this lot**: several of the app's existing CSS rules use descendant selectors (e.g. `.profile-fields input`) that are MORE specific than the new primitives' own base class (`.form-input`) -- so migrating a form's markup to the new primitives is not enough by itself; every old rule that would still match the primitive's internal elements has to be found and deleted/trimmed too, or the OLD styling silently keeps winning and the migration achieves nothing visually. Several of these old rules are shared, multi-selector blocks that also serve OTHER, not-yet-migrated forms (`VoiceView`, `AdminPanel`, `CreateChannelModal`) -- only the specific selectors belonging to the form actually being migrated can be removed from those shared rules; the rest must survive untouched. This was verified via grep before every deletion in both tasks, and the highest-risk case (`.channel-name-field`/`.create-channel-form select`, still live for the out-of-scope `CreateChannelModal`) was independently re-confirmed byte-for-byte untouched by a fresh reviewer reading the current files directly, not just the diff. **Any future Palier 2 work must budget real time for this same CSS archaeology per form** -- it is not a one-time cost paid off by Palier 1, since each additional form surfaces its own set of shared/dead rules.

- `screen-share-audio-fix`: on some Chrome/Edge + platform combinations, sharing a screen *with audio* silently failed with a generic "can't share" toast and no visible error. Root cause (traced into `livekit-client`'s source, corroborated against Chrome's documented `systemAudio`-capture platform support): `getDisplayMedia` rejects the *entire* capture call with `NotSupportedError` when the platform can't satisfy the requested `systemAudio` constraint at all -- it doesn't fail gracefully and hand back video-only. `toggleScreenShare` in `VoiceView.tsx` now catches that specific error at the `createScreenTracks` call and retries with `audio: false` explicitly overridden (the per-quality `screenProfiles[quality].capture` in `quality.ts` hardcodes `audio: true`, so a bare spread isn't enough), showing "Could not share this screen's audio here. Sharing video only." Any other capture error (e.g. `NotAllowedError` from a dismissed OS picker) is rethrown unchanged -- retrying that would just reopen a picker the user just closed. Heavy `console.log`/`warn`/`error` logging was added at every step of the capture/publish flow per explicit request, to make any future failure visible instead of silent. This complements, and sits on top of, an unrelated fix from another agent working in this codebase (`fix(voice): preserve screen share when audio fails`, `d33e98f`) that handles a *different* failure mode -- capture succeeding but the audio track's *publish to LiveKit* failing after the fact.

## Security fixes

- SVG attachments were served with `Content-Disposition: inline` (any client-supplied `image/*` MIME type was trusted), and the web client linked directly to that URL for anything it treated as an image -- a stored XSS, since SVG can carry `<script>`/event handlers that execute when opened as a top-level document. Fixed by restricting inline rendering to an explicit raster-image allowlist (`server/src/routes/messages.ts`'s `INLINE_SAFE_MIME_TYPES`, mirrored client-side in `web/src/layout/ChatView.tsx`); anything outside it, including SVG, is always forced to download, plus `X-Content-Type-Options: nosniff` and a restrictive CSP on that response. **Do not widen that allowlist back to a bare `startsWith("image/")` check.**
